## 当前结论

ESP32-S3 与 nRF52840 之间的基础 BLE 通信已经实机跑通，目前不是“通信失败”状态。

已确认链路：

1. ESP32-S3 作为 BLE Central，扫描 nRF52840 暴露的 Nordic UART Service。
2. S3 完成连接、通知订阅，并向 nRF52840 发送 JSON `hello`。

6. 既有实机记录表明 K1 单击、K2 单击、K2 长按均可经 BLE 回传至 S3。
7. `hardware_bridge --transport s3` 已具备 wearable 事件解包、按钮到 Agent 的路由及屏幕帧封装能力。

## 启动界面与任务 0 语音交互（17:31）

### 数据实际传输方式

**语音：** nRF52840 板载 PDM 麦克风采集 16 kHz、单声道、PCM16。固件将 PCM 分成 384 字节块，使用 Base64 放入换行分隔 JSON：`audio_start → audio_chunk(seq,audio) → audio_stop(chunks,dropped)`。为避免 BLE 带宽不足，S3 工作模式采用双链路：按钮和屏幕经 `S3 USB → BLE → nRF52840`，原始语音经 `nRF52840 USB → Mac`。Mac 将音频重组为 WAV，交给本地 MLX Whisper 中文转写，转写文本再提交 `/api/session/start` 创建任务。当前没有上传语音到云端。

**视频：** LRCP G720P 提供标准 UVC 视频流，系统已识别其设备和模式；当前项目尚未读取为 Agent context，也没有编码上传或云端视觉处理链路。因此目前不存在“视频传输到 S3/nRF”或“视频上传云端”的实现。

### 新启动和待机界面

nRF52840 固件已加入启动页：开机先显示 `MindLoop / Starting...` 约 1.2 秒，然后进入 `MindLoop Ready / K1: voice start/stop / Waiting for Agent`。桥连接 Agent 后，待机页由 Mac 渲染为：

- 主提示：`按 K1 开始语音输入`
- 底部提示：`再按 K1 结束并创建任务`

固件重新编译和烧录成功；25 项回归测试通过。启动页显示时间较短，桥建立后会被 Agent 页面覆盖，这是预期行为。

### 任务 0 的交互方式

在屏幕处于待机页面时：

1. 单击 K1，开始录音。
2. 对 nRF52840 板载麦克风说出任务，建议持续 1–10 秒。
3. 再单击 K1，停止录音。
4. Mac 将 PCM 重组为 WAV，并使用 MLX Whisper 转为中文文本。
5. 识别出的文本自动提交给 Agent；Agent 拆解任务后，第一步会显示回 nRF52840。

本轮新版桥已同时打开：

- S3 控制串口 `/dev/cu.usbmodem101`
- nRF52840 语音串口 `/dev/cu.usbmodem1101`

语音无法识别的根因已定位并修复：同一个 K1 事件原先同时经 BLE→S3 和 nRF USB 两路进入桥接队列，第一份事件启动录音，重复事件随即停止录音，因而稳定触发“录音太短”。新版桥现在让 nRF USB 只接收 `audio_start`、`audio_chunk`、`audio_stop`，按钮事件仅采用 BLE→S3 路径，并为两路串口使用独立缓冲区。新增重复按钮回归测试，完整测试现为 26 项且全部通过。

修复后的桥已启动并同时连接 `/dev/cu.usbmodem101` 与 `/dev/cu.usbmodem1101`。最终真人语音验收仍需一次实际操作：单击 K1，连续说话 2–5 秒，再单击 K1；成功标志是日志出现 `Voice captured ... transcript=...`，且 Agent 从 idle 进入 `action_ready`。

## 语音“传输过载”修复（17:49–17:55）

修复重复按钮后，用户遇到“音频传输过载”。为区分 USB 吞吐与并发阻塞，执行了 8 秒直接 USB 压力测试：收到 1,000 个连续音频块、256,000 字节，序号无间断，`dropped=0`。这证明纯 USB 音频路径稳定；过载更可能发生于录音状态切换时 BLE 屏幕刷新造成的短时阻塞。

处理如下：

- nRF52840 音频环形缓冲区从 8 KB 扩大到 32 KB，可覆盖约 1 秒 PCM16 音频。

- 固件重新编译通过：Flash 194,872 字节，RAM 58,084 字节（24%）。
- 26 项软件测试全部通过。

## 启动页 K1 无响应排查（18:13–18:26）

K1 硬件状态机本身能发出事件；无响应的直接原因是桥接器在录音期间收到 S3 的 `ble_disconnected` 后抛出异常并退出，之后 S3 与 nRF 两个串口均无人监听。

同时修复了两处按键语义冲突：

- 录音期间仅 `K1 single` 可以停止录音，K1 双击/长按及 K2 手势全部忽略，避免误触发撤回、新任务或反馈。
- completed 状态仅接受 K1 单击新建任务、K2 单击继续，其他手势忽略。

断线处理也改为非致命状态：桥保持运行、暂停向 wearable 发送屏幕与触觉命令，等待 S3 自动重连；收到新的 `ready` 后清除旧帧状态并恢复刷新。
